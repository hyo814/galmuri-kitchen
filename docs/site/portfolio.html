문제와 목표

장 본 재료를 끝까지 먹게 돕기

냉장고에 무엇이 있는지 기억에 의존하면 재료는 상해서 버려지고, 있는 걸 또 사고, 저녁마다 뭘 먹을지 고민하게 됩니다. 이 앱은 재고 기록을 출발점으로 레시피, 장보기, 식단까지 이어 가는 것을 목표로 합니다.

풀려는 문제

  • 두부·요거트처럼 포장 날짜를 확인하지 않으면 언제 상하는지 모르는 재료
  • 참기름·대파처럼 늘 있어야 하는데 떨어진 줄 모르는 필수품
  • 냉장실, 냉동실, 김치냉장고, 찬장에 흩어진 재고
  • 교체 시기를 놓치기 쉬운 코팅 프라이팬

목표와 제약

  • 네이티브 앱 없이 휴대폰 브라우저에서 동작 (실사용 기기 뷰포트 약 384px)
  • 비밀번호를 저장하지 않는 소셜 로그인(카카오·구글)
  • 단계마다 배포 가능한 상태 유지
  • 식품 안전 기준은 추정이 아니라 확인한 공공 참고값을 쓰고 출처를 남기기

내가 한 일

구현한 핵심 기능

설계 문서 작성, 단계별 구현 계획, 백엔드 API와 마이그레이션, 프론트엔드 화면, 테스트와 배포 준비까지 전 과정을 맡았습니다.

  • 재고와 보관 위치재료 등록·수정·삭제. 기본 냉장실·냉동실·실온에 사용자 정의 위치를 더하고, 위치마다 오래됨 기준(냉장 7일, 냉동 60일, 실온 없음)을 둡니다.
  • 임박·경고 배지D-2, 구입 16일째, 섭취 주의. 서버가 상태를 판정하고 임박 순으로 정렬해 내려줍니다.
  • 필수품 배너재고와 이름을 매칭해 떨어진 필수품을 첫 화면 배너로. 이름은 앞 3개와 “외 N개”만 보여 줘 화면을 차지하지 않게 했습니다.
  • 품목별 경고 규칙식약처 소비기한 참고값을 구입일 기준으로 환산해 기본 규칙으로 시드. 사용자가 수정·삭제할 수 있습니다.
  • 주방 도구도구 목록과 주기 점검. 이름에 코팅·프라이팬이 들어가면 6개월 점검을 미리 선택합니다(논코팅·무코팅 제외).
  • 하단 탭 5개재고 · 레시피 · 장보기 · 식단 · 더보기. 아직 만들지 않은 탭은 준비 중 화면으로 앞으로 나올 기능을 안내합니다. 탭 전환은 히스토리를 쌓지 않고, 더보기 → 주방 도구는 쌓아서 휴대폰 뒤로가기가 기대대로 동작합니다.
  • 인증Authlib 기반 카카오·구글 OAuth. 사설 IP는 리다이렉트 URI로 등록할 수 없어, DEV_MODE=1에서만 개발용 로그인을 열고 운영 환경에서 켜진 채 시작하면 거부합니다.
  • 재료 빠른 입력(1d)저장하고 계속 추가로 연속 등록, 단위 칩, 구입일 +N일 유통기한 빠른 입력, 수량 −/+ 스테퍼, 수량 0에서 다 썼어요로 바로 삭제. 이중 제출 방지 가드를 넣었습니다.
  • 재고 검색 · 필수품 시트 정리(1d)재고 이름 검색, 필수품의 떨어진 것만 보기, 떨어진 항목을 누르면 이름이 채워진 재료 추가로 연결, 있으면 매칭된 재고 이름을 함께 표시.
  • 매칭 오탐 차단(1d)짧은 이름 매칭 규칙을 다듬어 파가 양파를, 고추가 고추장을 잘못 잡지 않게 했습니다. 장류·소스로 등록한 필수품과 이름이 맞는 냉장 재료는 오래됨 배지에서 제외하되(고추장 불고기 같은 요리는 그대로 경고), 유통기한·품목 규칙 판정은 그대로 적용합니다.
  • 시작 화면과 브랜드(1d)셰프 다람쥐 다람이 스플래시, 앱 아이콘, 파비콘. 이름을 갈무리부엌으로 바꿨습니다.

앱의 실제 디자인 토큰과 치수로 그린 화면입니다. 화면 속 재료와 날짜는 2026년 9월 13일을 오늘로 둔 예시 데이터입니다.

Flask 한 앱이 React까지 서빙

backend · 배포
결정
Flask가 /api/*, /auth/*와 React 빌드 결과를 같은 오리진에서 내보냅니다. Docker 멀티 스테이지로 node에서 빌드하고 python 이미지에 복사합니다.
이유
CORS 설정이 필요 없고, 세션 쿠키를 HttpOnly·SameSite=Lax로 둔 채 상태 변경 요청에 X-Requested-With 헤더를 요구하는 방식으로 CSRF를 막을 수 있습니다. 배포 단위도 이미지 하나로 끝납니다.
대가
로컬에서는 Vite 개발 서버(5180)가 /api·/auth를 Flask(5181)로 프록시해야 합니다.

라우터 라이브러리 대신 해시 라우팅

frontend · 내비게이션
결정
#/, #/more, #/tools를 hashchange로 읽는 작은 훅. 모르는 경로는 #/로 돌립니다.
이유
화면이 셋뿐인 시점에 의존성 없이 휴대폰 뒤로가기를 살릴 수 있습니다. 탭 전환은 location.replace로 히스토리를 쌓지 않고, 더보기에서 들어간 화면만 pushState로 쌓아 뒤로가기가 한 단계씩 돌아갑니다.
교체 시점
경로 파라미터가 많아지면 React Router로 바꾼다고 코드 주석에 적어 두었습니다.

상태 판정 우선순위

backend · 도메인 규칙
결정
위에서부터 처음 해당하는 기준 하나만 씁니다.
  1. 유통기한을 입력했으면 그것만 봅니다. D-3 이내면 임박, 아니면 정상.
  2. 냉동실이면 품목 규칙을 쓰지 않고 60일 기준.
  3. 이름이 매칭되는 품목 규칙이 있으면 규칙(노랑 / 빨강 섭취 주의). 여러 개면 빨강 일수가 가장 짧은 규칙.
  4. 없으면 위치 종류 기준(냉장 7일, 실온 없음).
이유
처음에는 여러 기준 중 가장 심각한 상태를 고르는 방식이었습니다. 포장에 적힌 날짜를 직접 넣었다면 그 날짜가 가장 정확하고, 냉동 보관은 냉장 기준 참고값과 맞지 않습니다. 사용자와 순서를 정해 스펙 14절을 먼저 고친 뒤, 판정 로직을 우선순위대로 바로 분기하도록 단순화했습니다.

API 키 없이 도는 샘플 모드

설계 · 2단계부터 적용
결정
AI 스캔·레시피처럼 외부 키가 필요한 기능은 키가 비어 있을 때 개발 모드에서는 샘플 데이터로 동작하고, 운영에서는 기능을 숨깁니다. 설계와 환경 변수 문서에 정해 두었고 해당 기능을 구현할 때 적용합니다.

PostgreSQL에서도 같은 테스트를 실행

테스트 · 인프라
결정
평소에는 빠른 SQLite로 테스트하되, TEST_DATABASE_URL을 주면 같은 스위트를 실제 PostgreSQL에서 테스트마다 격리해 돌립니다. 배포 전에는 Postgres 대상 flask db upgrade와 db check, Docker 이미지 스모크 테스트까지 거칩니다.
이유
운영 DB는 PostgreSQL입니다. 마이그레이션, 외래 키 CASCADE, 정수 범위처럼 엔진마다 다르게 동작할 수 있는 부분을 배포 전에 로컬에서 확인하려고 했습니다.

데이터를 채우는 마이그레이션

보관 위치와 품목 규칙을 추가할 때 기존 사용자에게도 기본값을 넣고, 기존 재료는 냉장실로 옮기는 Alembic 마이그레이션을 테스트로 확인했습니다. 테스트는 마이그레이션 시점의 기본값을 리터럴로 고정해 비교하고, 기본값을 바꿀 때는 기존 마이그레이션이 아니라 새 마이그레이션을 추가하도록 했습니다.

Docker 이미지와 PostgreSQL

Render가 쓸 이미지를 로컬에서 빌드해 호스트 PostgreSQL에 붙여 실행. 비루트 사용자로 뜨는지, 첫 화면·/api/me 401·manifest 200 응답과 마이그레이션 로그를 확인했습니다.

배운 점

실제로 부딪힌 것들

  • 리뷰 반영이 만든 회귀

    시트를 닫을 때 포커스를 돌려주려고 언마운트 정리 함수에서 dialog.close()를 부르게 고쳤습니다. 그런데 개발 모드 StrictMode는 마운트, 정리, 마운트를 한 번씩 더 실행하고, 그 close 이벤트가 부모의 onClose를 불러 모든 시트가 열리자마자 닫혔습니다. 다음 리뷰에서 잡아 되돌리고 이유를 주석으로 남겼습니다.

    네이티브 요소에 부작용을 거는 effect는 두 번 실행돼도 안전한지 먼저 따집니다.

  • 눈으로 본 대비는 틀린다

    승인된 시안의 초록·보조 글자·경고 색은 화면에서 충분히 읽혔지만, 계산해 보니 라이트 테마에서 AA에 못 미쳤습니다. 사용자 승인을 받아 토큰을 한 톤 진하게 바꿨고, 이후 다크 테마의 보조 글자색도 기준에 모자란 것을 찾아 한 톤 밝혔습니다.

    대비는 시안 단계에서 토큰 쌍으로 계산해 확인합니다.

  • 요구사항은 도중에 늘어난다

    구현 중에 식단·영양 계산기, 매장 장보기, 쇼핑몰 정렬 링크, 양념 비율 계산기, 주방 도구가 추가됐습니다. 매번 진행 중인 코드에 끼워 넣지 않고 docs/* 브랜치로 설계 문서에 날짜와 함께 먼저 반영했고, 판정 순서처럼 이미 만든 동작이 바뀔 때도 스펙을 먼저 고쳤습니다.

    문서를 먼저 고치면 진행 중인 브랜치의 범위가 흔들리지 않습니다.
